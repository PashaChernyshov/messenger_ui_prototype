# Корпоративный XMPP-мессенджер

Flutter-приложение корпоративного мессенджера с темной деловой темой, feature-first архитектурой и интеграцией с XMPP. Проект ориентирован на desktop/mobile Flutter и реализует базовые сценарии корпоративной коммуникации: контакты, личные чаты, групповые MUC-комнаты, профиль, настройки, фильтры, вложения и историю сообщений.

## Текущее состояние

Проект переведен из прототипа в более структурированную модель приложения:

- реализовано подключение к XMPP-серверу;
- выполняется авторизация через SASL PLAIN;
- поддерживается STARTTLS;
- загружается roster контактов;
- импортируются XMPP bookmarks;
- импортируются и открываются MUC-группы;
- выполняется вход в MUC-комнаты;
- подтягиваются участники групп через presence;
- поддерживается отправка и получение личных сообщений;
- поддерживается отправка и получение групповых сообщений `type='groupchat'`;
- реализована загрузка истории через MAM;
- UI приведен к единому корпоративному стилю;
- структура проекта разнесена по слоям `app`, `core`, `features`;
- логика XMPP изолирована от UI.

## Архитектура проекта

Проект организован по feature-first подходу. Это сделано, чтобы новый разработчик мог быстро найти нужный модуль, не смешивать UI, бизнес-логику и инфраструктуру, а также развивать приложение без превращения кода в монолит.

```text
lib/

    theme/
  core/
    ui/
    widgets/
  features/
    calls/
    chat/
    contacts/
    groups/
    profile/
    settings/
    shell/
    xmpp/
```

## Слой `features`

Каждая feature разделена на подслои:

- `domain` - доменные модели;
- `data` - репозитории и источники данных;
- `presentation` - экраны, виджеты, view models.

Такое разделение приближает проект к SOLID:

- UI не должен знать детали хранения данных;
- XMPP-протокол не должен быть размазан по экранам;
- доменные модели не зависят от виджетов;
- репозитории инкапсулируют хранение и доступ к данным;
- сервисы отвечают за инфраструктуру.

## Feature: XMPP

Путь:

```text
lib/features/xmpp/
  data/
    xmpp_service.dart
  domain/
    connection_status.dart
    xmpp_bookmark.dart
    xmpp_chat_message.dart
    xmpp_room_presence.dart
```

### `xmpp_service.dart`

Низкоуровневый XMPP-сервис. Он инкапсулирует протокол и не зависит от экранов.

Реализовано:

- TCP-подключение к серверу на порт `5222`;
- открытие XML stream;
- STARTTLS;
- SASL PLAIN авторизация;
- bind resource;
- session request;
- отправка initial presence;
- загрузка roster через `jabber:iq:roster`;
- отправка личных сообщений `type='chat'`;
- получение входящих личных сообщений;
- загрузка MAM-архива;
- загрузка legacy bookmarks через `jabber:iq:private`;
- загрузка pubsub bookmarks через `urn:xmpp:bookmarks:1`;
- вход в MUC-комнату через presence с `http://jabber.org/protocol/muc`;
- отправка групповых сообщений `type='groupchat'`;
- получение groupchat сообщений;
- парсинг MUC presence;
- поток входящих сообщений;
- поток presence участников комнаты.

### Доменные модели XMPP

`XmppChatMessage` описывает сообщение XMPP:

- id;
- peer JID;
- from JID;
- to JID;
- body;
- timestamp;
- outgoing;
- archived;
- groupChat.

`XmppBookmark` описывает XMPP bookmark:

- JID комнаты;
- название;
- nick.

`XmppRoomPresence` описывает presence участника MUC:

- room JID;
- participant id;
- nick;
- available/unavailable.

## XMPP: что работает

На текущем этапе работает:

- подключение к серверу;
- авторизация;
- импорт контактов из roster;
- импорт групп из bookmarks;
- подключение к MUC-комнатам;
- получение участников групп через presence;
- отправка личных сообщений;
- отправка групповых сообщений;
- получение входящих сообщений;
- загрузка истории через MAM, если сервер ее отдает;
- fallback-загрузка личной истории через общий MAM-архив с фильтрацией по JID.

## Ограничения XMPP

Некоторые данные зависят от настроек сервера:

- если roster на сервере пустой, приложение не может получить контакты как roster;
- если MUC скрывает реальные JID участников, приложение видит только nick;
- если история Gajim хранится только локально, сервер не отдаст ее через MAM;
- для web-сборки нужен WebSocket/BOSH, потому что браузер не поддерживает прямой TCP/5222;
- статусы online/offline требуют дальнейшей доработки presence-логики;
- delivery/read receipts требуют отдельной реализации XEP.
